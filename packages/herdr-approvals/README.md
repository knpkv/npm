# `@knpkv/herdr-approvals`

Host runtime, fleet CLI, approval PWA, push worker, and shared Rly shell for the Herdr packages.

It publishes two binaries:

- `hostd`: local fleet authority plus optional Tailscale listeners, approvals, Connect, and push
- `fleetctl`: status, history, job submission/following, Work checkpoint recording/snapshots, and fleet-wide apply submission with per-host outcomes

`hostd` reads `FLEET_CONFIG_PATH`, defaulting to `~/.config/fleet/config.json`. The file is decoded by `@knpkv/herdr-fleet`; invalid or missing fields fail startup. With `crossHost: false`, the loopback listener, the Work-only listener bound to `workBindAddress` (loopback by default), and immediately queued safe jobs are available, with no Tailscale dependency. Cross-host listeners authenticate the actual socket peer with Tailscale WhoIs. Forwarded identity headers are never trusted.

Consumers that own durable orchestration import `makeHostdProgram` and `HostdOperationsComposer` from `@knpkv/herdr-approvals/hostd-runtime`. The composer receives the decoded host configuration, the package's default typed operations, and a narrow `fork` function that registers work for the hostd process lifetime without exposing its closeable scope. It may decorate the typed `run` and `runCoordinatorChat` methods while reusing every default status, local recovery, and command adapter. Each run receives the accepted job ID and actor, the existing `workerStarted` callback, and a typed lifecycle callback. The required `AgentDelegate.mode` distinguishes ordinary `consult` work from `transition_summary`; durable adapters project those to Luna medium and Luna low respectively, without reading prompt text or defaulting an unknown intent. Status and wait remain outside model dispatch, while `review` and `work` remain Sol high. A durable adapter supplies `recovery.matches` and `recovery.resume`. It submits one `OrchestratorCommand`, calls `lifecycle.accepted` with its durable receipt, returns that receipt, and registers later queue, run, worker binding, and terminal work through `fork`. Fleet marks matching jobs durable before invocation, persists the receipt separately, and keeps the wrapper running until `lifecycle.terminal` mirrors `settled`, `delivery_failed`, or `task_failed` from the coordinator. After restart, `recovery.resume` receives the same deterministic job ID, fresh callbacks, either the receipt or `null`, and the exact persisted worker or `null`. The `null` receipt path resubmits the same idempotency key to close the crash window after coordinator commit but before Fleet receipt persistence; it must not create a second request. A present worker is reattached by replaying `workerStarted` without a new prompt. Terminal values are explicit bounded Fleet summaries produced with `summarizeHostOperationTerminalDetail`; full authoritative values remain in coordinator events. Consumers stream those durable events by request ID from the same coordinator instance. They call its authoritative `workerStarted` before the fleet callback so Work and Connect receive the same worker identity. A failed Luna dispatch becomes a new Sol dispatch through `submitSolEscalation` and `OrchestratorLinkedSolDispatchReference`. The accepted v2 Work handoff supplies both its bounded context delta and immutable expected revision; the adapter uses that persisted revision at worker start instead of refreshing lane authority.

The normalized receipt is intentionally client-visible: Fleet stores it in `acceptedReceipt` and `result`, and authorized raw job and history routes expose it. It must not contain provider callback URLs, bearer tokens, credentials, or server-private locators. Recovery registers observation through `fork` and returns before terminal completion so listener startup cannot be held open by durable work.

`makeHostdProgram` does not run an Effect runtime or provide Node services. The executable `hostd` keeps the existing default operations and owns one Node runtime. An embedding consumer owns that same single runtime. A composer that cannot build its required durable runtime fails startup with `HostdOperationsCompositionError`; there is no implicit retry or fallback to a different adapter. The composer receives no raw command executor, raw Herdr input, repository selector, or session selector. Approval and HTTP authorization stay inside hostd. The composer also receives `hasOutstandingWorkJob`, which says whether any Work job (admit, recover, reconcile, reassign, abandon) in hostd's job store is still to run: waiting for approval, approved and queued, or running. A pending approval past its expiry no longer counts, even while it is still stored as pending. Those jobs' preflight tokens hash the whole Work store until they run, so a background writer defers its Work writes while it is true. Composed without a job store, it fails with `FleetStoreError` rather than answering no. The composer also receives `startedWorker(jobId)`: the worker Fleet's job record says that job started (host, agent id, name, pane), or null when the job is unknown or started none. It is the authority for which agent a job started; pane metadata is not, since any local agent can write it. A job store that can't be read, or a composition without one, fails with `FleetStoreError` rather than answering null.

The default operations run `nix.apply` as the configured apply command followed by two arguments: the ref, then the Fleet job id. The job id lets the apply command record that job's own outcome, so a host that restarts mid-apply can settle the job from it. An apply command that takes only the ref must ignore a second argument.

On the approval hub, `approvalTls` names absolute certificate and private-key paths owned by the hostd user. The hub terminates TLS directly on its configured Tailscale IP and `approvalPort`; certificate provisioning and renewal remain host policy. Non-hub tailnet members keep their plain tailnet listeners. Local-only machines do not read TLS material or invoke Tailscale.

Fleet-wide submission preserves partial results. One unreachable host does not erase successful submissions to other hosts, but the command exits with a typed failure after printing all outcomes. The runtime performs no Tailscale mutation; Nix remains responsible for certificates, ACLs, node enrollment, secrets, and service lifecycle.

Approval mutations require the exact active listener origin, including HTML form submissions. Originless fleet submission remains a separate authenticated CLI path. Only hostd sets submission provenance, never the request body, which rejects unknown fields. A `POST /v1/jobs` on the local listener that passed loopback authorization and carries no proxy header (`Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `Via`) is a verified local submission: its `nix.*` and `agent.*` jobs queue without approval. Every other listener or proxied request is remote, and Work authority jobs always wait for approval. Existing browser push subscriptions are reconciled with the server on page load, so server-side expiry or revocation cannot leave a false enabled state.

## Approval request disclosure

The authenticated approval browser receives a sanitized projection of each request from the persisted `JobRecord`. Pending, approved, rejected, and expired records retain the same typed request fields in browser-visible history. Safe fields include the request kind and title, operation mode and channel, normalized repository or revision coordinates, agent session, actor and worker identities, and lifecycle timestamps. Repository and revision values are redacted for credentials and unsafe URI query parameters before they cross the HTTP boundary; internal prompts and messages are represented by `[redacted internal prompt]`.

Approval nonces, job hashes, command results and errors, credentials, subscription details, raw terminal or internal prompts never appear in the authenticated browser projection or any unauthenticated/public response. Other authenticated host activity may appear through its own sanitized projection; it is not part of this approval-request disclosure. The projection is not a substitute for the persisted `JobRecord`; approval decisions still require the authenticated listener and server-side nonce/hash proof.

`pushAllowedOrigins` is the exact HTTPS-origin allowlist for browser push services. Subscription endpoints are checked before persistence and again before delivery; credentials, IP literals, localhost, and origins outside that list are rejected. Add self-hosted push services explicitly by their public origin.

The approval hub renders one masthead and three tabs. Approvals contains only local decisions and remote approval handoffs. Connect embeds the package terminal and authoritative relationship tree, and is the hub's one agent list: each agent's state, its work, and its terminal. The hub has no coordinator chat: it has no `/v1/chat` route, and its page polls no chat. A coordinator chat job queued before the upgrade still runs through Fleet's `runCoordinatorChat`, and its reply stays on its job record. Work renders the durable `@knpkv/herdr-work` projection and job history; it does not list agents. The built PWA assets keep offline installation, push subscription management, notification click routing, and the same authenticated browser routes.

`fleetctl work record HOST CHECKPOINT_JSON` decodes one `WorkGoalCheckpoint` locally, then posts it to the target host's fixed `POST /v1/work/checkpoints` endpoint. With `crossHost: false`, Work uses a Work-only listener on the explicitly configured IPv4 `workBindAddress` and port (loopback by default); its only routes are the schema-decoded `GET /v1/work` snapshot and originless typed checkpoint POST. Wildcard bind addresses are rejected, and requests must use the exact configured listener authority so an unconfigured DNS alias cannot read the snapshot. With `crossHost: true`, Work commands target only the canonical approval hub, which serves the read-only snapshot and typed checkpoint route through its authenticated tailnet/TLS surface. An omitted `fleetctl work snapshot` host targets the canonical hub in cross-host mode and the local host otherwise. Checkpoint writes reject browser-origin requests and accept no job, command, file, or partial-goal shape. A checkpoint containing an approval target requires cross-host approval to be enabled, the host to be configured, and the approval page to resolve through the configured hub or an online Tailscale peer; its URL origin must exactly match that resolved page before persistence. Disabled cross-host approval, unknown or offline hosts, Tailscale failures, malformed approval pages, and origin mismatches return typed validation or operation failures without recording a new checkpoint. An exact persisted replay remains idempotent when its approval page is temporarily unavailable; changed content with the same event ID or goal timestamp returns `WorkCheckpointConflictError`.

Set the optional `agentLimitsCommand` in the fleet configuration (for example `["/home/me/.local/bin/agent-limits", "--json"]`) to report this host's Claude and Codex subscription windows. The command must print the `agent-limits` v1 JSON contract. hostd runs it once at start, then serves its last read and reruns it in the background once that read is 30 seconds old, so a slow run never delays an answer and serves the result at `GET /v1/limits` on every listener that serves the dashboard. On the canonical hub, the same route lists every peer's read, which it fetches from each peer's tailnet `GET /v1/limits/local`; only the approval hub's node may call that peer route. A host without the command, a failing or slow command, a newer contract, or output that is not the contract is reported as `Unavailable` with its own reason. A peer the hub could not ask is listed under `failures`. If the hub cannot list the fleet at all, it answers with its own read and `peersListed: false`. An unknown window keeps its reason and is never reported as zero use. The command reads only local files; no provider token crosses these routes.

Set the optional `lanWork` object in the fleet configuration to opt into a LAN Work listener (or pass the equivalent `HttpServerOptions.lanWork` when embedding the server). It exposes `/pair`, `/`, and `GET /v1/work`, plus the static Work stylesheet at `/assets/index.css` and configured `.woff2` fonts. The server prints a lowercase 64-character code after the listener is ready; the code is accepted once in a POST body, expires after five minutes, and is never placed in a URL. The paired session is an HttpOnly cookie. Approvals, Connect, secrets, agent control, and job submission remain unavailable on this listener. Top-level `GET /` and `GET /pair` navigations may omit `Origin`; the pairing `POST /pair` and authenticated `GET /v1/work` API require the exact listener origin and reject missing or different origins before reading or authorizing the request.

LAN Work deliberately serves plain HTTP and is suitable only for a trusted LAN segment. It does not provide transport confidentiality; put an authenticated TLS proxy or equivalent private network boundary in front of it before exposing pairing codes or session cookies across an untrusted link. Provider locators remain server-private; LAN Work exposes only normalized client-visible records or recorded-target status.
